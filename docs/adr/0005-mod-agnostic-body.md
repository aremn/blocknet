# ADR-0005: Тело не знает модов по имени

- Статус: Принято (2026-10-27)
- Пересмотреть, если: для заметной доли машин в целевых сборках общий слой не даёт ни состояния,
  ни управления, и адаптеры начинают обрастать общей логикой.

## Контекст

Бот должен работать в больших сборках с сотнями модов. Если учить его модам по одному
(«вот так AE2, вот так Mekanism»), код превратится в набор частных случаев и будет ломаться с
каждой новой сборкой. При этом у NeoForge и Minecraft есть общие механизмы, через которые моды
и так открывают своё устройство игроку и друг другу.

## Решение

- Всё, что бот делает с модовым контентом, идёт через общий слой:
  - блоки и предметы — по реестру, тегам и состояниям блоков;
  - машины — через capabilities NeoForge: предметы, жидкости, энергия, по сторонам;
  - интерфейсы — через меню и слоты сервера (`containerMenu`), их видит любой мод;
  - рецепты — через `RecipeManager`, включая типы рецептов модов.
- Адаптер под конкретный мод пишется, только если общий слой физически не даёт нужного. Пример:
  содержимое сети AE2 терминал показывает не слотами, а своими пакетами. Адаптер реализует общий
  интерфейс (например, `StorageNetwork`), подключается только когда мод загружен и не добавляет
  логики в тело.
- Реальные моды в репозитории — только тестовая среда (`localRuntime` + `ModdedBlockGameTests`):
  тесты проверяют поведение, а не конкретный мод, и тестовый мод можно заменить.

## Последствия

- Новая сборка в основном работает без кода под неё: у машин есть capabilities, у интерфейсов — меню.
- Протокол с мозгом говорит общими словами (`machine.inspect`, `menu.*`, `storage.*`), без имён модов.
- Часть удобств (настройка сторон, режимы, кнопки, работающие своими пакетами) появится только там,
  где для мода есть адаптер.
