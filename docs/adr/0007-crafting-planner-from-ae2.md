# ADR-0007: Планировщик крафта из AE2, отдельным LGPL-модулем

- Статус: Принято (2026-10-27)
- Пересмотреть, если: планировщику понадобятся модовые машины, и модель AE2 (узел на предмет,
  процесс на рецепт) перестанет подходить.

## Контекст

Боту нужен инструмент «как сделать N предметов X из того, что есть»: дерево рецептов с тем, что
берётся из инвентаря, что крафтится и сколько раз, на какой станции, чего не хватает и что останется.
LLM вызывает его сама, когда считает нужным, и не должна считать дерево в токенах (ADR-0006).

JEI дерево не строит: он показывает рецепты и раскладывает их в сетку. В AE2 есть проверенный
расчёт заказа (`CraftingCalculation`, `CraftingTreeNode`, `CraftingTreeProcess`): сначала взять
из симулированного инвентаря, потом перебрать рецепты в дочерней симуляции, подменять ингредиенты
тегов, не уходить в циклы, учитывать остатки (вёдра) и недостающее. Код AE2 под LGPL-3.0, наш мод
под MIT.

## Решение

- Переносим алгоритм AE2 в отдельный Gradle-подпроект `crafting/` (`dev.blocknet.crafting`) под
  LGPL-3.0-or-later, устроенный как `pathing/` (ADR-0004): свой LICENSE, `GAMELIBRARY`, вложенный
  jar в моде. Файлы, взятые из AE2, сохраняют указание авторства и пометку об изменениях.
- Типы сети AE2 (ключи, шаблоны, CPU) заменяются нашими: ключ предмета, процесс из рецептов
  Minecraft, снимок инвентаря.
- Рецепты берутся из `RecipeManager` без имён модов (ADR-0005): верстак и сетка 2x2, печи с топливом,
  камнерез, кузнечный стол. Рецепты других типов (модовые машины) пока только упоминаются в подсказке.
- Сначала только план. Выполнение крафта — отдельный шаг, через тот же серверный код, что
  срабатывает при клике игрока по книге рецептов.

## Последствия

- Изменения в `crafting/` публикуются под LGPL вместе с исходниками, как и `pathing/`.
- Остальной мод зовёт планировщик через его API и остаётся MIT.
