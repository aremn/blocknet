# Содержимое сетевых хранилищ через открытый терминал

Статус: этапы 1 (чтение) и 2 (вывод/ввод предметов, источник для планировщика) реализованы 2026-10-29. Целевая версия: Minecraft 1.21.1,
AE2 19.2.18 (`gradle.properties`). Это продолжение ADR-0005: общий интерфейс в теле,
зависимые от мода классы только в необязательном адаптере.

## Что показала игровая сессия

В `brain/logs/session-2026-10-28T18-40-13-474Z-pidor.jsonl`:

- 18:57:15 UTC: `use p2` открыл `ae2:craftingterm`, 51 обычный слот.
- 18:57:17: `menu` показал физические слоты меню, но не виртуальный список сети.
  Пустые слоты крафта и view cells не означают пустую сеть.
- 19:02–19:03: бот поставил controller, creative_energy_cell, drive и crafting_storage.
- 19:03:20: кабель был отклонён `place` как `not a block item`.

Последняя проблема исправляется общим `useItemOn` для предметов. Она независима от чтения сети.
Наличие crafting storage не доказывает наличие ячейки хранения в drive; будущий интерфейс должен
различать пустую подключённую сеть, отключённый терминал и неподдерживаемое меню.

## Почему обычных слотов недостаточно

Проверены исходники тега `neoforge/v19.2.18` в `_src/ae2` и сигнатуры runtime jar 19.2.18:

- `MEStorageMenu.broadcastChanges()` получает `storage.getAvailableStacks()`, отдельно считает
  craftable keys и отправляет `MEInventoryUpdatePacket`. Это не `menu.slots`.
- `getPreviousAvailableStacks()` возвращает последний серверный снимок, но метод protected.
- `isKeyVisible(AEKey)` фильтрует ключи, `getLinkStatus()` описывает подключение.
- `ITerminalHost.getInventory()` рассчитан на однократное получение при открытии меню.
  Не следует заново получать его на каждый запрос или обращаться напрямую к дискам.
- `handleInteraction(serial, InventoryAction)` выполняет действия терминала на сервере,
  проверяет подключение и использует энергию и action source игрока.

Источники: [MEStorageMenu, 19.2.18](https://github.com/AppliedEnergistics/Applied-Energistics-2/blob/neoforge/v19.2.18/src/main/java/appeng/menu/me/common/MEStorageMenu.java),
[ITerminalHost, 19.2.18](https://github.com/AppliedEnergistics/Applied-Energistics-2/blob/neoforge/v19.2.18/src/main/java/appeng/api/storage/ITerminalHost.java),
[официальный обзор API](https://github.com/AppliedEnergistics/Applied-Energistics-2/blob/neoforge/v19.2.18/API.md).
Онлайн Javadoc относится к более новым версиям и не заменяет проверку закреплённого jar.

## Этап 1: только чтение открытой сети

1. Ввести общий SPI `NetworkMenuAdapter` и неизменяемый `NetworkSnapshot`. Поиск адаптера идёт
   по реальному `containerMenu`; `MenuAccess` не импортирует классы AE2. Обычные сундуки остаются
   на текущем пути. Классы адаптера и optional mixins загружаются только при наличии AE2;
   без него мод запускается с прежним набором возможностей.
2. Адаптер принимает уже открытое меню. На серверном потоке проверяет, что оно ещё принадлежит
   боту, совпадает `containerId`, `stillValid(bot)` и терминал подключён. Не ищет сеть через
   мир, координаты контроллера или глобальные сетевые сервисы.
3. Получать уже сформированный серверный снимок после обычного `broadcastChanges`, через
   изолированный optional invoker `getPreviousAvailableStacks()`. Применять `isKeyVisible`;
   не менять коллекцию меню. Если снимок ещё не готов, вернуть `pending` и дождаться тика.
   Invoker — внутренняя интеграция, поэтому совместимость с 19.2.18 проверяется отдельно.
4. Ключ снимка: бот, dimension, открытое меню, revision. Строка: тип ресурса, registry id,
   components, количество `long`, единица измерения и при наличии отдельный признак craftable.
   В первом этапе хранить только реальные количества; craftable без запасов не считается запасом.
   Неизвестные типы ресурсов обозначать явно, жидкости не считать предметами.
5. Расширить `menu` отдельным разделом `network`, сохранив физические слоты. Для больших сетей:
   фильтр, ограниченная страница, total kinds и opaque continuation token, привязанный к revision.
   При изменении снимка запрашивать страницу заново. Внутренние счётчики остаются `long`;
   в JSON передавать точные десятичные строки, чтобы не потерять числа больше 2^53 в Node.
6. Статусы: `ready`, `empty`, `disconnected` с причиной, `pending`, `unsupported`, `stale`.
   `unsupported/disconnected/stale` не сохранять как пустой инвентарь. Разрыв питания или канала
   должен немедленно делать прежний снимок недействительным.
7. На первом этапе снимок нужен для ответа «что в сети». Не добавлять его в
   `ContainerMemory.sources()` и рецептный планировщик: пока нет исполнения вывода из сети,
   обещать получение этих предметов нельзя. Память помечает снимок как последнее наблюдение.

## Что сделано на этапе 1

- Общий слой `control/NetworkMenus` (Adapter, Snapshot, статусы READY/EMPTY/DISCONNECTED/PENDING)
  и раздел `network` в `menu` (bridge-параметры `filter?`, `page?`). Тело не знает классов AE2.
- `compat/Compat` — единственное место соответствия mod id → класс адаптера; класс грузится по имени
  только при наличии мода. `compat/ae2/Ae2TerminalAdapter` + `compat/mixin/ae2/MEStorageMenuMixin`
  (отдельный `blocknet_ai.compat.mixins.json`, `CompatMixinPlugin` применяет mixin только при
  загрузке мода). AE2 — `compileOnly` для сборки, в рантайме зависимости нет.
- Mixin только читает `previousAvailableStacks`/`previousCraftables` и считает серверные
  `broadcastChanges`: ноль = `pending`. Видимость — `isKeyVisible`, подключение — `getLinkStatus()`.
- Вывод текстовый: количества `long` печатаются точными десятичными числами, craftable без запаса
  идёт отдельной строкой и не входит в запас. Страница `<menu_id>.<revision>.<offset>` по 40 строк;
  revision меняется при изменении содержимого, старая страница отклоняется.
- Отступление от пункта 7: снимок сети пока не сохраняется в память контейнеров вообще,
  только читается из открытого меню.
- `NetworkMenuGameTests`: сеть с питанием и пустой ячейкой → `empty`, затем бот сам кладёт предметы
  quick-move'ом → точные количества, отдельная запись для предмета с компонентами, фильтр, отказ
  старой страницы; без питания → `disconnected`, ни разу не `empty`.
- Не проверено GameTest'ом: запуск без AE2 (в dev-рантайме он всегда есть), craftable-ключи
  (нужны шаблоны и CPU), жидкости, ограничение доступа терминалом.

## Этап 2: вывод и ввод через действия терминала

После независимой проверки чтения расширить SPI выполнением действий. Ключи и serial существуют
только внутри конкретного меню и revision, их нельзя повторно использовать после переоткрытия.

- Вывод: те же `handleInteraction` и `InventoryAction`, что использует игрок. Не вызывать напрямую
  `MEStorage.extract/insert` в обход меню, энергии и прав. Проверять фактическое изменение
  инвентаря/курсора, полное место, частичные результаты и изменение сети другим игроком.
- Ввод: реальные предметы из инвентаря и стандартный путь курсора/quick move. Сохранять задержку
  между кликами, отмену и безопасное возвращение курсора как у `ContainerTask`.
- После этого подключить сетевые источники к `withdraw/deposit/obtain` и crafting planner,
  используя существующее правило одного перепланирования. Одинаковую сеть за двумя терминалами
  нельзя считать двумя независимыми запасами; до появления надёжного network identity использовать
  только один сетевой источник на план.
- Автокрафт сети, беспроводные терминалы и жидкости — отдельные последующие задачи.

## Что сделано на этапе 2

- SPI `NetworkMenus.Adapter`: `handles`, `pickup` (клик по сохранённому предмету пустым курсором —
  до одной стопки на курсор), `putCarried` (клик курсором по пустой области сети: всё или один).
  AE2-адаптер вызывает `MEStorageMenu.handleInteraction` с serial, который терминал уже отправил
  экрану (`IncrementalUpdateHelper.getSerial` через mixin), — серверную половину клика игрока.
  Энергия, каналы и доступ решает сеть; прямых `extract/insert` нет.
- `ContainerTask` (общий для withdraw/deposit/look-in и планировщика) в сетевом режиме: вывод —
  стопка из сети на курсор, раскладка в инвентарь левым/правым кликом, остаток обратно в сеть;
  ввод — стопка из инвентаря на курсор, в сеть целиком или по одному. Пауза 3 тика между кликами,
  таймаут фазы сбрасывается при каждом успешном предмете. Отмена возвращает курсор в сеть.
  Свежепостроенная сеть «загружается»: до 40 тиков `disconnected` ждём, потом честный отказ.
  Отказ сети (нет ячейки, переполнение) сообщает, что уже перемещено. `transfer` с терминалом
  явно не поддержан.
- `ContainerMemory` запоминает терминал как запись `network` с реальными количествами сетевых
  предметов (без craftable и без сетки крафта терминала); `disconnected` стирает прежний снимок,
  `pending` ничего не меняет. В `sources()` попадает только ближайший сетевой терминал.
- GameTests: ввод 40 и вывод ровно 25 по одной стопке 64+6, остаток 15 виден через look-in,
  затем крафт печи берёт 8 булыжника из сети по памяти; сеть без ячейки отказывает и все предметы
  остаются у бота.
- Не сделано: жидкости, беспроводные терминалы, network identity (AE2 не даёт id сети, переживающего
  перезапуск; правило «один сетевой терминал на план» остаётся).

## Автокрафт (2026-10-29)

`autocraft {ref, item, count}` идёт путём игрока: клик `AUTO_CRAFT` в терминале открывает
`CraftAmountMenu`, `confirm(amount, false, autoStart=true)` открывает `CraftConfirmMenu`, AE2 планирует
с `REPORT_MISSING_ITEMS` и сам отправляет задание. Бот сообщает «submitted», нехватку конкретных
предметов, отказ сети или отсутствие свободного CPU. Готовый результат забирается обычным `withdraw`.
Терминал «спиной» к боту открывается кликом по другой части кабеля (`partAims`).
GameTest: пустая сеть → «short of 1 oak_log», после `deposit` бревна → «autocraft submitted».

## Проверки и критерии готовности

| Проверка | Ожидаемый результат |
|---|---|
| Сеть с питанием, drive, настоящей storage cell и терминалом | Точные запасы совпадают с содержимым ячейки; физические слоты терминала остаются отдельными |
| Та же сборка без storage cell | `empty`, без придуманного запаса из crafting storage |
| Отключено питание/нет канала | `disconnected`, причина; предыдущие запасы недействительны |
| Закрыто меню, бот отошёл, сменил dimension или умер | `stale`; чтение и действия прекращаются |
| Предметы с одинаковым id и разными components | Разные записи и точные количества |
| Изменение другим игроком | Новый revision; старая пагинация и serial отклоняются |
| Терминал ограничивает доступ/тип ключей | Не выдавать данные или ресурсы сверх доступного игроку |
| Огромное количество и много видов | Без int/JS округления, ограниченный вывод, измеренный бюджет тика |
| Craftable key без запаса | Не входит в stored amount и не удовлетворяет `inv >= N` |
| Запуск без AE2 и с обычным сундуком | Нет class-loading/mixin ошибок; прежние меню работают |
| Вывод с неполным местом, отмена посреди кликов (этап 2) | Фактический частичный результат, ни потерь, ни дублирования |

Новые GameTests используют реальные fixture-моды и собирают сеть через игровые действия;
начальные ресурсы задаёт только тестовая сцена. Добавить Node-проверки статусов, больших чисел,
устаревших страниц и невозможности выдать unsupported за пустую сеть. Затем полный offline build,
полный набор GameTests с проверкой summary/исключений и существующие Node suites.
